## 2. Live-pod diagnosis (520 / 502 / blank screen)
**Tooling limitation:** `get_pod_events` could not be read — the platform returned `kubectl_failed: cluster deployment-cluster-03 not found` on both attempts. So exact **restart count** and **OOMKilled** reason are NOT retrievable right now. Findings below come from pod logs + tier config.

**What the logs show (active run ff4976a3):**
- One clean backend startup (00:14:47, `uvicorn … --workers 1`, "Application startup complete"); no restart loop visible within the window.
- Repeated nginx errors every ~10s: `upstream timed out (110: Connection timed out) while reading response header from upstream … GET /health … http://127.0.0.1:8001/health` (00:15:29–00:16:59), plus an initial `connect() failed (111: Connection refused)` during boot.
- Backend workload warnings in the same window: `candles_deep page failed (… 1d): MT5 request timed out`, `candle refresh … WARNING`, plus synchronous backtest/profiling work ("profiled XAUUSD: 70 backtest trades …").

**Mechanism of the 520/502 (confirmed from logs):** the single uvicorn worker's event loop is intermittently **blocked** by synchronous heavy work (pandas backtests) and slow/timing-out MT5/MetaApi RPC calls. While blocked, nginx's 1s health/upstream read to :8001 times out → nginx emits a 503/invalid/empty response → Cloudflare surfaces **520 "could not parse response"** and **502 Bad Gateway**. This cleanly explains why a heavy `POST /api/alerts/test` 502'd while cached `GET` endpoints (`/api/trades/account`, `/api/trades/scan-status`) returned 200.

**Correlation answer:** the 520/empty-responses correlate with **backend event-loop stalls / upstream timeouts** — directly visible. I could NOT confirm correlation with pod **restarts or OOM** (pod events unreadable; logs show no restart in-window). So "crash-looping/OOM-killed" is **unconfirmed**, not ruled out.

## 3. Resource limits (tier_0 "Starter")
- CPU: request 50m / **limit 250m**. Memory: request 200Mi / **limit 512Mi**. Replicas 2 (no HPA/VPA).
- 250m CPU is a severe ceiling for an app running pandas backtests + a persistent MetaApi socket.io stream + background loops. CPU throttling at this limit is a strong, plausible driver of the event-loop stalls and /health timeouts above. 512Mi memory is also tight for pandas workloads.
- Recommendation: raise to tier_1+ (Deployment Panel → Resources) to relieve CPU throttling / memory pressure. (OOMKilled could not be confirmed due to the pod-events read failure, but the CPU ceiling aligns in time with the failures.)
